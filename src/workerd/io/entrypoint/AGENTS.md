# io/entrypoint/

## OVERVIEW

The `entrypoint` crate: a Rust `WorkerEntrypoint`, which receives one event for a Worker's exported handler, and the events that Rust delivers. It owns the C++ `WorkerEntrypoint` (`io/worker-entrypoint.{h,c++}`), seen as an `entrypoint::CxxEntrypoint` (`io/entrypoint-invocation.h`), which makes the event's request. `WorkerEntrypoint::construct()` always returns the Rust one.

C++ callers reach it through `RustWorkerEntrypoint` in `ffi.c++`, a `WorkerInterface` that sends an event Rust implements to Rust and every other event straight to the C++ object, with no Rust in between: an unported event costs one more allocation for the Rust object, one for `RustWorkerEntrypoint`, and one virtual call. For an event that Rust delivers, the C++ object hands Rust an `entrypoint::Invocation` (`io/entrypoint-invocation.h`): the `IoContext::IncomingRequest` the event was made for and what finds the exported handler (entrypoint name, version info, props). Rust reports the event to the tracer, delivers it, starts the handler and finishes the request. The calls on the request are `io_context`'s bindings of `IoContext::IncomingRequest` (`io-context/ffi.h`); this crate's `ffi.h` only reaches into its own `Invocation`, starts the scheduled handler and finds the exported handler (see "Porting C++ to Rust" in `io/AGENTS.md`). The crate is on the runtime side of the [Rust seam](../../../../docs/reference/rust-seam.md).

Two events are delivered this way:

- **The scheduled event** (`WorkerEntrypoint::runScheduled()`, `scheduled.rs`), behind its own autogate, `RUST_ENTRYPOINT_SCHEDULED`, which `RustWorkerEntrypoint::runScheduled()` checks: with it, the Rust object takes the C++ object's invocation, and without it, the event goes to the C++ object. Its JavaScript half, `ServiceWorkerGlobalScope::startScheduled()` with the `ScheduledController` it creates, stays in C++: both paths start it with `entrypoint::startScheduledInWaitUntil()` (`io/entrypoint-invocation.{h,c++}`).
- **The test event** (`WorkerEntrypoint::test()`, `test.rs`), with no autogate, since only test runners deliver it. `RustWorkerEntrypoint` passes it to the C++ object, whose `test()` hands it to Rust with `entrypoint::runTest()`. Its handler runs in Rust: `Delivered::run_test_in_wait_until()` runs a Rust function in a waitUntil task with `io_context::incoming_request_run_in_wait_until()` (C++ `context.addWaitUntil(context.run(...))`), on the handles that `entrypoint::getTestHandles()` finds in the run's C++ prelude (`io_context::RunPrelude`), and the test-api crate calls the handler's `test()` with a Rust `TestController`. Finding `test()`, and failing under Service Workers syntax or without one, stays in C++, in `ServiceWorkerGlobalScope::getTestHandler()`, so the event fails with the exceptions it throws.

## KEY FILES

| File           | Role                                                                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lib.rs`       | `WorkerEntrypoint`, which owns the C++ one. `Invocation` → `Delivered` → `Running`: each step consumes the value it is called on, so each happens once and in order. Dropping a delivered event destroys its request without draining it, as C++ does after a failed step |
| `scheduled.rs` | The scheduled event's steps, in the order `WorkerEntrypoint::runScheduled()` takes them in C++                                                        |
| `test.rs`      | The test event's steps, and the function that calls the handler's `test()`                                                                            |
| `ffi.rs`       | The cxx bridge, and the Rust functions C++ calls (`worker_entrypoint_new`, `scheduled_event_*`, `test_event_*`)                                       |
| `ffi.h/c++`    | Access to the `Invocation`'s request and handler, the scheduled handler's start, `RustWorkerEntrypoint`, and `newWorkerEntrypoint()` and `runTest()`, which `worker-entrypoint.c++` calls |

## CONVENTIONS

- **C++ is called when a step is called**, not when a future it returns is first polled. A step that waits returns a future for the wait only, so the request is in the state the step leaves it in once the step returns, as in C++. `RustWorkerEntrypoint::runScheduled()` and `runTest()` keep this across the boundary by splitting into a synchronous start and an async finish, so that an exception before the wait is thrown from them, as in C++.
- **No C++ JSG in `ffi.c++` / `ffi.h`.** They are in `CPP_SHIMS` (`src/rust/jsg/BUILD.bazel`), with no allowlist entries, so `//src/rust/jsg:cpp-jsg-allowlist-test` fails on any use. Code that needs C++ JSG belongs in `src/workerd/io` or `src/workerd/api`, in a function that the C++ path calls too, so that the two paths can't drift apart (as `startScheduledInWaitUntil()` is). No C++ JSG runs while Rust holds the isolate lock either: C++ work that a run does before it calls Rust, such as `getTestHandles()` finding the exported handler, which can construct a class, is the run's `io_context::RunPrelude`, which `io-context` runs in `IoContext::run()` before it enters Rust. An exception it throws, as from a throwing constructor, propagates as from the C++ lambda.
- **A function run in a waitUntil task fails with an `io_context::RunError`**: a JavaScript error, which `IoContext::run()` logs as uncaught, or a KJ exception, which it gets unchanged, as from C++ code.
- **Perfetto spans keep the C++ path's names.** A step in Rust emits its span with `perfetto::trace_event!` (`util/perfetto`), never held across an `.await`; a span that covers a wait, as the C++ path's `WorkerEntrypoint::test() waitForFinished()` does, is a `perfetto::AsyncSlice` held until the wait ends, on a track of its own. A span around C++ work that both paths share stays in that C++ code, as `WorkerEntrypoint::runScheduled() run` does in `startScheduledInWaitUntil()`. A run's span is named by its C++ prelude (`RunPrelude::spanName()`, a string literal), as `WorkerEntrypoint::test() run` is. `entrypoint::runScheduled()` marks the scheduled event's Rust path, and the Rust path emits `WorkerEntrypoint::runScheduled()` itself, since the C++ method doesn't run on it. `server/tests/scheduled:scheduled-perfetto-test` and `server/tests/test-event:test-event-perfetto-test` check them.
- **One autogate per event.** Each event that production requests reach is moved behind an autogate of its own, which no later change renames or widens. An event that only workerd's own commands deliver (`test()`, `bench()`) needs none.
- **The scheduled event's C++ path stays until the autogate is removed.** Until then, a Worker sees the same behaviour on both paths. A difference that no Worker can observe, such as one that only a runtime bug reaches, is documented where the Rust path makes it, as `Running::finish_scheduled()` does for `finishScheduled()`'s exceptions. `api/tests:scheduled-test` (its `@all-autogates` variant takes the Rust path) and `server/tests/scheduled` check both.

## NOT YET PORTED

- `bench()`: `workerd bench`'s event, once `BenchController` is in Rust.
- `ScheduledController` and `startScheduled()` in Rust, which would make the scheduled event's JavaScript half Rust as well.
- `request()` and `connect()`, which keep the C++ object's state (the request's `cf` blob, client address, whether to tunnel exceptions, the response-sent trackers, fail-open proxying).
- `worker::Interface` for the Rust `WorkerEntrypoint`, once `request()` is in Rust. `RustWorkerInterface` then replaces `RustWorkerEntrypoint`, and the per-event bridge entry points (`scheduled_event_*`, `test_event_*`) become the interface's methods.
