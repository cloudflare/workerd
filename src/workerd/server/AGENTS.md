# server/

## OVERVIEW

The `workerd` binary and its server. `:workerd` (`workerd.rs`, this package) is a Rust binary over three crates in this directory:

- `cli/` -- the `workerd-cli` crate (declared in this package's `BUILD.bazel`, sources globbed from `cli/`): parses the command line (clap), produces the encoded config (schema files are compiled by this package's `config-compiler.c++`), handles `compile`, `--watch` and re-exec, and hands `serve` and `test` (which `fuzzilli` and `make-pyodide-baseline-snapshot` are built on) to the server crate's `entry` module.
- `server/` -- the `workerd-server` crate: the single-tenant server. It interprets the config, builds the service graph, binds the sockets, runs the listeners, actors and dynamic workers, drains on SIGTERM, and runs `workerd test`. `Error` is `cxx::KjError`; `bridge.rs` is the one module that allows `unsafe`.
- `factory/` -- C++: `WorkerFactory` (`worker-factory*`), everything that needs the isolate, driven by the server through the cxx bridge in `server/bridge.rs`; and `bootstrap.{h,c++}`, the C++ half of a command. `with_process_context` sets up the process's logging (the JSON logger, when the config asks for structured logging) on the C++ stack around the Rust command; `bootstrap` sets up perfetto, autogates and V8 on the Rust-owned event loop and builds the `WorkerFactory`, which owns them, from the encoded config and the command-line options for `server/entry.rs`, which owns the loop (`kj_rs_tokio::Runtime`) and blocks on `server_serve` / `server_test`.

This package keeps the config schema (`workerd.capnp`, `compiled-bindings.capnp`), the config compiler, the `WorkerdApi` and the C++ libraries the factory is built from (alarm scheduler, channel tokens, container client, facet tree index, fallback service, actor IDs, JSON logger, Pyodide, V8 platform), and their C++ unit tests.

**The Rust/C++ boundary.** The factory keeps everything that touches the isolate: compiling a worker (`WorkerdApi`, compatibility flags, extensions, modules), starting a request on it, constructing actors with their storage, alarms and containers, the capnp RPC servers, channel-token encoding and the inspector. It also keeps the single-tenant policy objects, which live in this directory because the production runtime supplies its own: the unlimited `LimitEnforcer`, the clock-corrected `TimerChannel`, the null `IsolateLimitEnforcer`, the default observers. The server owns everything else: config interpretation, bindings and channel numbering, services, listeners, actor lifecycle and eviction, dynamic workers, drain and the test runner. Every bridge function on the C++ side is a free function taking the object first; one that can throw is declared fallible (a C++ exception becomes a `Result` error), the rest do not throw. A `KjOwn` moves ownership in the direction of the call, a `Box` of a Rust type handed to C++ is a cheap `Rc` or `Weak` handle C++ may hold.

Crossing the boundary:

- **Bindings cross as one message** (`server/bindings.rs`, `server/channels.rs`; their module docs have the detail). `compile_bindings` interprets `Worker.bindings` into `Globals` (`compiled-bindings.capnp`), every capability a channel number, and `loopback_globals` does the same for `ctx.exports`; the factory compiles the message into `env` and `ctx.exports` under the isolate lock, and at request time the runtime asks the worker's `ChannelFactory` (Rust) for the channel behind a number. A dynamic worker's `env` arrives as KJ capabilities already, so the factory keeps them as the worker's own tables (`CompiledWorker::Impl`), together with its global outbound and tails, and asks the Rust `ChannelFactory` only for the channel numbers past them: the worker's `ctx.exports`, which the server numbers from the counts `WorkerInfo` reports.
- **Workflows are wired after every service exists.** `workflowsEngine` gets two passes in `server/config.rs`: `collect_workflow_configs` (with the actor configs) checks it and synthesizes the `Durable` config of each valid Workflow's namespace, keyed `miniflare-workflows-<name>` and carrying the `Workflow` (name, class, `bindingService`) the later pass reads; `init_workflows` (after the services) resolves the engine's class and the `bindingService`, builds the actor props (`workflowClass` stub, `workflowClassName`, `workflowName`) with the `frankenvalue_*` shims and creates the namespace on the app worker (`WorkerService::init_workflow_namespace`), its storage in the bindingService worker's directory. The bindings compiler gives each configured Workflow a subrequest channel to its bindingService (`workflow_binding_channels`), the inner fetcher of the Workflow's wrapped `ctx.exports` binding; a Workflow class takes no loopback channel.
- **Background tasks run on the KJ loop** (`server/tasks.rs`, whose module doc says why): spawn with `Factory::spawn` / `spawn_detached`, which put the future in the factory's `kj::TaskSet`; never with `kj_rs_tokio::spawn`.
- **`loopback:<name>` addresses** (`server/listen/loopback.rs`) are in-process connections, refused unless the registry is enabled, which only `workerd test` and the in-process server (`server/in_process.rs`) do. An HTTP or TCP listener serves a connection with its hang-up signal (`listen/mod.rs`, `hangup`) and a dialer hands one to kj-hyper's client: `LoopbackStream::hangup`, or a socket's `kj_rs_io::when_write_disconnected`.
- **`--control-fd`** (`Control`, `server/run.rs`): `listen-inspector` and `listen` events, one JSON object per line with `port` last; a config the `Reporter` refuses gets no `listen` event. The server writes to a duplicate of the descriptor (`cli/socket_fd.rs`).
- **Header names the config chooses are table headers** (`buildHeaderTable`, `factory/worker-factory.c++`): the factory's `kj::HttpHeaderTable` holds every header the config's `HttpOptions` name, so kj writes them as the config spells them and the rewriter (`services/rewriter.rs`, whose module doc has the rest) edits `kj::HttpHeaders` by name.
- **Logging** (`server/log.rs`): log from the server with `tracing::error!` / `warn!` / `info!`, which become KJ log lines through `kj_log`. Config errors and warnings go to the `Reporter` (`server/config.rs`), which `entry.rs` prints to stderr, as it does `Tests failed!` and the run's failure (`*** Uncaught exception ***`): as they are, or, under structured logging, as lines of the JSON logger's format (`json_log_to_stderr`, over `buildJsonLogMessage`). The logger's own lines (`KJ_LOG`, `tracing`, the workers' consoles) go to stdout; what supervises the process (miniflare) reads the reason of a failed start from stderr. An error is printed the way KJ prints an exception through `exception_text` (`kj::str`: `file:line: type: description`; a `KjError` carries no stack trace, and one made in Rust has the bridge's location). Every error is reported and the server then does not serve, unless `--watch` is on.

Bazel labels: `//src/workerd/server:workerd` (and `:workerd_cross`, which `wd_test` runs), `//src/workerd/server:workerd-cli`, `//src/workerd/server/server:workerd-server` (its bridge library `:bridge.rs@cxx`, whose header is `<workerd/server/server/bridge.rs.h>`), `//src/workerd/server/factory:worker-factory` / `:bootstrap` (header-only `:worker-factory-hdrs` / `:bootstrap-hdrs` for the bridges). The Rust packages hold only `.rs` files; the bridges take their C++ headers from `cxx_bridge_deps`.

## TEST INFRASTRUCTURE

- **Rust unit tests**: a module's tests are in the `<module>-test.rs` beside it (`config-test.rs` for `config.rs`, `listen/mod-test.rs` for `listen/mod.rs`), compiled only into the crates' test targets (`//src/workerd/server/server:workerd-server_test`, `//src/workerd/server:workerd-cli_test`); see `src/rust/AGENTS.md`, UNIT TEST FILES. The server crate's test binary links `//src/workerd/util:setup-async-io` because the C++ it reaches calls `kj::setupAsyncIo()`.
- **C++ unit tests** (`*-test.c++`, `kj_test`): alarm scheduler, channel tokens, container client, facet tree index, fallback service, JSON logger, actor IDs.
- **`server-test.c++`** (`//src/workerd/server:server-test@`): the server end to end, in the test process. Each `TestServer` builds a `WorkerFactory` on the test's V8, timer, network and a temp directory, and hands it to `InProcessServer` (`server/in_process.rs`, through the server crate's bridge), which runs `run::run` / `run::test` on it and queues the config errors and warnings for the test. No connection but UDP's leaves the process: the config's socket and external addresses become `loopback:` names, the test connects to the server's sockets and accepts the server's outbound connections by name (the `network` services' too), and the factory's own C++ clients (Docker, the debug port) dial the same names through the test's `kj::Network`. The factory's timer is the test's mock `kj::TimerImpl`, which `test.wait(n)` advances; the server's own delays run on it too (`Factory::sleep` / `Factory::now`, `server/config.rs`). An unexpected error log, config error or warning fails the case, as does a factory still referenced once the server is closed. Add a case here for every new config error or warning.
- **`tests/`**: `server-harness.mjs`, a Node.js harness spawning the `workerd` binary for E2E tests; it reads the `listen` events off `--control-fd`. Subdirectories: `compile-tests`, `container-client`, `container-shutdown`, `extensions`, `inspector`, `module-fallback`, `python`, `socket-close`, `structured-logging`, `udp-connect`, `udp-connect-ts-streams`, `udp-datagram-drop`, `unsafe-eval`, `unsafe-module`, `weakref`, `wrapped-binding-serialization`. Every `.wd-test` in the repository also runs through `workerd test` (`wd_test` in `build/wd_test.bzl`, over `:workerd_cross`).
- **kj-hyper contract tests** (`src/rust/cxx/kj-hyper/tests`): HTTP and WebSocket semantics against kj's interfaces.
- `:rust-io-link-check` inspects the linked binary's symbols (unix): kj's own `setupAsyncIo()` must not be linked in.

## I/O: THE TOKIO EVENT LOOP

- One thread, one loop: `server/entry.rs` creates a `kj_rs_tokio::Runtime` (the KJ event loop
  on kj-rs-tokio's port, with its tokio `current_thread` runtime) and `block_on`s the command,
  which runs as a task on the loop's `LocalSet` while the main thread is blocked in
  `promise.wait()`: the KJ loop schedules the thread, and tokio runs whenever it sleeps. The
  factory takes its `kj::Timer` from the Runtime's context and its `kj::Network` from a kj-rs-io
  provider the bootstrap builds over it, so the C++ side (actor storage, alarms, RPC, containers)
  sees KJ I/O interfaces over tokio. The Rust server binds its sockets and dials external
  servers through kj-rs-io's Rust API (`TokioAddress`: KJ's address grammar, resolver and socket
  options), which hands back tokio's sockets (`server/listen/`, `server/services/`); a `network`
  service resolves and connects with tokio itself (`kj_hyper::client::connect_allowed`). HTTP in
  both directions is hyper through kj-hyper, SIGTERM is `tokio::signal`, `loopback:` is
  `tokio::io::duplex`.
- `kj::setupAsyncIo()` (which `//src/workerd/util:setup-async-io` supplies over kj-rs-tokio and
  kj-rs-io) is the same loop for the threads that block on a `kj::WaitScope` from C++: the
  inspector and fallback-service threads, and every `kj_test` binary.
- `setup-async-io` is linked per BINARY: `:workerd` (through `factory:bootstrap`) and every
  `kj_test` / `wd_cc_benchmark` binary link it (the macros add it); libraries do not depend on
  it, so a downstream binary linking workerd libraries keeps its own event loop. One exception
  for now: `//src/workerd/tests:test-fixture` still carries the dep so downstream binaries that
  link it without linking it themselves keep linking (TODO(cleanup) there; drop it once they
  depend on `setup-async-io` or `@capnp-cpp//src/kj:kj-async` themselves).
- Never depend on the `@capnp-cpp//src/kj:kj-async` umbrella: it drags in `kj-async-os`, whose
  definitions collide with the shim's (an ODR violation). Use `:kj-async-core` / `:kj-async-io`.
  `just check-io-backend-graph` (one `bazel cquery somepath`, run by the lint CI lane) rejects any
  such path from `:workerd`; `:rust-io-link-check` inspects the linked binary's symbols on unix.
- Ownership: the returned `kj::AsyncIoContext` borrows a heap holder attached to its
  `lowLevelProvider`; the holder owns the tokio context and the inert event port, so the context's
  references are valid for its whole lifetime and torn down once. The inert `kj::UnixEventPort` is
  never driven (`KJ_UNIMPLEMENTED` if anything tries). I/O objects are used on the loop thread that
  created them (kj-rs-io checks and throws otherwise); the server's `Rc` state, kj-hyper's objects
  and the `loopback:` registry are likewise bound to the loop thread.
