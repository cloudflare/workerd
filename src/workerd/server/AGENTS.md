# server/

## OVERVIEW

The `workerd` binary and its server. `:workerd` (`workerd.rs`, this package) is a Rust binary over three crates in this directory:

- `cli/` -- the `workerd-cli` crate (declared in this package's `BUILD.bazel`, sources globbed from `cli/`): parses the command line (clap), produces the encoded config (schema files are compiled by this package's `config-compiler.c++`), handles `compile`, `deploy` (cluster mode), `repl` (`cli/repl/`, over the C++ in `repl/`), `--watch` and re-exec, and hands `serve`, `test` (which `fuzzilli` is built on) and `bench` to the server crate's `entry` module.
- `repl/` -- C++: the isolate side of `workerd repl` (experimental, behind `--experimental`). `ReplEnvironment` evaluates input in a worker with one IoContext for the whole session, whose `workerd` global (`repl-api.h`) loads configs. Each loaded config runs on a `WorkerFactory` of its own under `InProcessServer` (`repl-server.h`), its stream sockets (HTTP, HTTPS, TCP) on `loopback:` names; the REPL reaches its services and sockets through the server's host channels (`server/in_process/host.rs`). Usage and design: `docs/repl.md`.
- `server/` -- the `workerd-server` crate: the single-tenant server. It interprets the config, builds the service graph, binds the sockets, runs the listeners, actors and dynamic workers, drains on SIGTERM, and runs `workerd test` and `workerd bench`. `Error` is `cxx::KjError`; `bridge.rs` is the one module that allows `unsafe`.
- `factory/` -- C++: `SharedFactory` and `WorkerFactory` (`worker-factory*`), everything that needs the isolate, driven by the server through the cxx bridge in `server/bridge.rs`; and `bootstrap.{h,c++}`, the C++ half of a command. A `SharedFactory` is what the loop threads of a process share and is thread-safe (the config and options, V8, the header table and the header IDs each loop's capnp factory and `ThreadContext` use, the memory caches, the channel token key, the inspector's registrar); a `WorkerFactory` is one loop thread's, over it (timer, network, capnp factories, `ThreadContext`, `ChannelTokenHandler`, task set, the thread's Rust server, containers), and every `CompiledWorker` belongs to the loop of the factory that compiled it. Only the primary loop's factory (`PrimaryLoop`) registers isolates with the inspector, starts it, opens Durable Object storage, and serves the sessions over which the other loops reach its actors (`factory_accept_loop_session`). `with_process_context` sets up the process's logging (the JSON logger, when the config asks for structured logging) on the C++ stack around the Rust command (`thread_logger` and `run_with_logger` install it on another thread's stack); `bootstrap_process` sets up perfetto, autogates and V8 once and builds the `SharedFactory`, which owns them, from the encoded config and the command-line options; `bootstrap_loop` builds a loop thread's `WorkerFactory` on that thread's loop; `bootstrap` does both for `server/entry.rs`, which owns the loop (`kj_rs_tokio::Runtime`) and blocks on `server_serve` / `server_test` / `server_bench`. The binary runs one loop thread, or with `workerd serve --threads=<N>` (experimental) N of them (see I/O: THE TOKIO EVENT LOOP).
- `cluster/` -- the `cluster` crate and, in `cluster/logic/`, `cluster-logic`: cluster mode (`Config.cluster`, experimental), Durable Objects whose shared state is a bucket: S3-compatible (`s3.rs`, SigV4) or Google Cloud Storage (`gcs.rs`, the XML API with generation preconditions; tokens from `google_auth.rs`). Leases, ownership, LTX capture and restore, and deployments (`deploy.rs`: named applications in the bucket, which every node serves beside its own config by the rules of `compose.rs`); pure Rust, driven by `server/cluster.rs` and, for deployments, `cli/deployments.rs`. `cluster-logic` holds decisions only, with no dependencies to do I/O with.

This package keeps the config schema (`workerd.capnp`, `compiled-bindings.capnp`), the config compiler, the `WorkerdApi` and the C++ libraries the factory is built from (alarm scheduler, channel tokens, container client, facet tree index, fallback service, actor IDs, JSON logger, V8 platform), and their C++ unit tests.

**The Rust/C++ boundary.** The factory keeps everything that touches the isolate: compiling a worker (`WorkerdApi`, compatibility flags, extensions, modules), starting a request on it, constructing actors with their storage, alarms and containers, the capnp RPC servers, channel-token encoding and the inspector. It also keeps the single-tenant policy objects, which live in this directory because the production runtime supplies its own: the unlimited `LimitEnforcer`, the clock-corrected `TimerChannel`, the null `IsolateLimitEnforcer`, the default observers. The server owns everything else: config interpretation, bindings and channel numbering, services, listeners, actor lifecycle and eviction, dynamic workers, drain, the test runner and `workerd bench`'s report. Every bridge function on the C++ side is a free function taking the object first; one that can throw is declared fallible (a C++ exception becomes a `Result` error), the rest do not throw. A `KjOwn` moves ownership in the direction of the call, a `Box` of a Rust type handed to C++ is a cheap `Rc` or `Weak` handle C++ may hold.

Crossing the boundary:

- **Bindings cross as one message** (`server/bindings.rs`, `server/channels.rs`; their module docs have the detail). `compile_bindings` interprets `Worker.bindings` into `Globals` (`compiled-bindings.capnp`), every capability a channel number, and `loopback_globals` does the same for `ctx.exports`; the factory compiles the message into `env` and `ctx.exports` under the isolate lock, and at request time the runtime asks the worker's `ChannelFactory` (Rust) for the channel behind a number. A dynamic worker's `env` arrives as KJ capabilities already, so the factory keeps them as the worker's own tables (`CompiledWorker::Impl`), together with its global outbound and tails, and asks the Rust `ChannelFactory` only for the channel numbers past them: the worker's `ctx.exports`, which the server numbers from the counts `WorkerInfo` reports.
- **Workflows are wired after every service exists.** `workflowsEngine` gets two passes in `server/config.rs`: `collect_workflow_configs` (with the actor configs) checks it and synthesizes the `Durable` config of each valid Workflow's namespace, keyed `miniflare-workflows-<name>` and carrying the `Workflow` (name, class, `bindingService`) the later pass reads; `init_workflows` (after the services) resolves the engine's class and the `bindingService`, builds the actor props (`workflowClass` stub, `workflowClassName`, `workflowName`) with the `frankenvalue_*` shims and creates the namespace on the app worker (`WorkerService::init_workflow_namespace`), its storage in the bindingService worker's directory. The bindings compiler gives each configured Workflow a subrequest channel to its bindingService (`workflow_binding_channels`), the inner fetcher of the Workflow's wrapped `ctx.exports` binding; a Workflow class takes no loopback channel.
- **Background tasks run on the KJ loop** (`server/tasks.rs`, whose module doc says why): spawn with `Factory::spawn` / `spawn_detached`, which put the future in the factory's `kj::TaskSet`; never with `kj_rs_tokio::spawn`.
- **`loopback:<name>` addresses** (`server/listen/loopback.rs`) are in-process connections, refused unless the registry is enabled, which only `workerd test`, `workerd bench` and the in-process server (`server/in_process.rs`) do. An HTTP or TCP listener serves a connection with its hang-up signal (`listen/mod.rs`, `hangup`) and a dialer hands one to kj-hyper's client: `LoopbackStream::hangup`, or a socket's `kj_rs_io::when_write_disconnected`.
- **`--control-fd`** (`Control`, `server/run.rs`): `listen-inspector`, `listen-cluster` (the cluster peer port, before the sockets' events) and `listen` events, one JSON object per line with `port` last; a config the `Reporter` refuses gets no `listen` or `listen-cluster` event. With several loop threads the first writes them, once every thread is ready to accept. The server writes to a duplicate of the descriptor (`cli/socket_fd.rs`).
- **Header names the config chooses are table headers** (`buildHeaderTable`, `factory/worker-factory.c++`): the factory's `kj::HttpHeaderTable` holds every header the config's `HttpOptions` name, so kj writes them as the config spells them and the rewriter (`services/rewriter.rs`, whose module doc has the rest) edits `kj::HttpHeaders` by name.
- **Logging** (`server/log.rs`): log from the server with `tracing::error!` / `warn!` / `info!`, which become KJ log lines through `kj_log`. Config errors and warnings go to the `Reporter` (`server/config.rs`), which `entry.rs` prints to stderr, as it does `Tests failed!` and the run's failure (`*** Uncaught exception ***`): as they are, or, under structured logging, as lines of the JSON logger's format (`json_log_to_stderr`, over `buildJsonLogMessage`). `cli/deployments.rs` queues the lines that say which deployments are served or skipped; `entry.rs` prints them through the same path. The logger's own lines (`KJ_LOG`, `tracing`, the workers' consoles) go to stdout; what supervises the process (miniflare) reads the reason of a failed start from stderr. An error is printed the way KJ prints an exception through `exception_text` (`kj::str`: `file:line: type: description`; a `KjError` carries no stack trace, and one made in Rust without a location has the location of the `cxx::KjException::from` that converts it). Every error is reported. The server does not serve after an error unless `--watch` is on or `workerd serve` attributes the error to a cluster deployment. In cluster mode, an unresolved reference from the node's config is logged as a deployment reference and does not stop the node. A deployment error leaves the server serving and does not change its exit status. Broken deployment services reject requests and actor construction.

Bazel labels: `//src/workerd/server:workerd`, `//src/workerd/server:workerd-cli`, `//src/workerd/server/server:workerd-server` (its bridge library `:bridge.rs@cxx`, whose header is `<workerd/server/server/bridge.rs.h>`), `//src/workerd/server/factory:worker-factory` / `:bootstrap` (header-only `:worker-factory-hdrs` / `:bootstrap-hdrs` for the bridges). The Rust packages hold only `.rs` files; the bridges take their C++ headers from `cxx_bridge_deps`.

- **`server-test.c++`** (`//src/workerd/server:server-test@`): the server end to end, in the test process. ## I/O: THE TOKIO EVENT LOOP

- A loop thread has one loop and one `WorkerFactory`. The binary runs one, the main thread,
  unless `workerd serve` is given `--threads=<N>` (experimental), which adds N-1 replicas
  (`server/threads.rs`, whose module doc has the order of startup, failure, drain and teardown).
  A replica has its own `Runtime`, its own factory over the same `SharedFactory`
  (`bootstrap_loop`), and its own `Server`: it compiles its own copy of every Worker (a Worker's
  global scope runs on every thread, its startup `console.log` lines appear N times, the startup
  snapshot and the isolates' memory are paid per thread, a `workerLoader` loads a dynamic Worker
  per thread, a named one from what its `getCode` callback returns on that thread, so threads
  can run different code under one name if the callback's answer changes) and builds its own services and client pools from the same config, which numbers
  channels the same way on every thread, so a binding or a channel token resolves within the
  thread. The threads share the listening stream sockets: the first binds them and hands each
  replica a duplicate (`kj_rs_io::TokioListener::duplicate`), of which the replica makes a
  listener on its own loop, so the kernel gives a connection to whichever thread accepts it
  first. The first thread alone reports config errors (a replica whose graph has one fails the
  process), handles SIGTERM and tells the others to drain, writes the `--control-fd` events
  once every thread is ready, and serves the UDP sockets, cron triggers and `--debug-port`.
  More than one thread is refused as a usage error with `--inspector-addr` or an option that
  saves a Python snapshot (`cli/args.rs`, `threads_refused`; the server reports the inspector
  as a config error too, `threads::obstacles`), and on Windows whatever else is given
  (`args::Platform`): there, a server on several threads at times left a connection unanswered
  that the system had accepted for it, for reasons not yet known. `workerd test` and
  `workerd bench` run one thread.
- **Durable Objects are the first loop thread's.** Every actor runs there, as with one thread:
  only its namespaces open storage (and with it the alarm scheduler) and hold `ActorContainer`s,
  so facets, containers, hibernated WebSockets and alarms are there too, and so is what is built
  on Durable Objects (Workflows, whose namespace is synthesized on the app worker, and the
  wrangler-derived KV, queues, D1 and cron Workers). A replica keeps one session with the first
  thread (`threads::FirstThread`, held by its `Factory`): a capnp `WorkerdDebugPort` session, the
  one a cluster instance keeps with a peer, over a `tokio::io::duplex` pipe made as the replica
  starts, served there by `factory_accept_loop_session`. A replica's `ActorNamespace` forwards
  (`ActorNamespace::forwards`): `link` opens nothing, and the channel of a stub is a
  `ForwardedChannel`, a capability from `getActor` (the service, the class or Workflow key, the
  hex id or ephemeral name, and the name the id was derived from) for the channel the first
  thread's namespace gives a stub of its own (`resolve_debug_actor` with `local_caller`, which
  takes `ActorNamespace::channel`, not `peer_channel`). The first thread therefore holds the
  container (`Client`) while the replica holds the stub and for each request in flight, the idle
  shutdown and the container sweep see a replica's stub as a local one, and a dropped stub
  releases its hold when the capability is released. A request is a `startEvent` on it: HTTP
  with streamed bodies, `connect()`, WebSockets (a hibernatable one stays open on the replica's
  connection while the actor hibernates) and JS RPC cross as capnp, in the order one stub's
  calls were made; stubs, service bindings and classes passed in JS RPC cross as channel tokens,
  which each thread resolves in its own graph, so the actor gets its own thread's. A stub whose
  source is an actor is restored from a replica (`restore()`) by an event on the same
  capability (`restoreService`, `restoreRpcStub`): the parameters' capabilities cross as channel
  tokens too (`LoopFrankenvalueHandler`), and the first thread builds from the actor's channel
  and the parameters the channel a `restored` token of its own decodes to
  (`ChannelTokenHandler::restoredSubrequestChannel` / `restoredRpcChannel`), so `[restore]()`
  runs there as for a stub of that thread, and a restore chain continues on what it returns.
  Only a loop session does this; a session with another instance (a cluster peer, an external
  server) refuses the event, and the stub's calls fail with an error that says so
  (`getInstanceFrankenvalueHandler`). Limits of the hop, which a call from the first thread
  itself does not have: the callee does not see the caller's trace span (`parentSpan`,
  `userSpanParent`); a `restore()` whose parameters hold a capability whose channel token is
  not available synchronously is refused, since the event is sent as it is written;
  `abortAllDurableObjects()`, `deleteAllDurableObjects()` and the eviction test hooks act on
  the thread they are called on and fail on a replica, which has no actors.
- **A cluster instance's part in the cluster is the first loop thread's**: the `ClusterNode`
  with its lease, ownership, capture, alarm index, peer port and sessions exists once per
  process. A replica does not join; its Durable Object calls go to the first thread as above,
  which routes them as its own (owned here, on a peer, or being handed off), and its `bucket`
  and `cache` services are the first thread's too (`services::ForwardedService`). Deployments are
  merged into the config before any thread starts, and a replica attributes their errors as
  the first thread did (`Reporter::replica_deployments`). On SIGTERM the replicas serve for as
  long as the first thread does (through the handoff and the grace period), then every thread
  stops accepting, and the first thread waits for the replicas' connections as for its own.
- `server/entry.rs` creates a `kj_rs_tokio::Runtime` (the KJ event loop
  on kj-rs-tokio's port, with its tokio `current_thread` runtime) and `block_on`s the command,
  which runs as a task on the loop's `LocalSet` while the main thread is blocked in
  `promise.wait()`: the KJ loop schedules the thread, and tokio runs whenever it sleeps. The
  factory takes its `kj::Timer` from the Runtime's context and its `kj::Network` from a kj-rs-io
  provider the bootstrap builds over it, so the C++ side (actor storage, alarms, RPC, containers)
  sees KJ I/O interfaces over tokio. The Rust server binds its sockets and dials external
  servers through kj-rs-io's Rust API (`TokioAddress`: KJ's address grammar, resolver and socket
  options), which hands back tokio's sockets (`server/listen/`, `server/services/`); a `network`
  service resolves and connects with tokio itself (`kj_hyper::client::connect_allowed`). HTTP in
  both directions is hyper through kj-hyper, SIGTERM is `tokio::signal`, `loopback:` is
  `tokio::io::duplex`.
- One exception to "one thread": a cluster node keeps its lease on the `cluster-lease` thread
  (`cluster/keeper.rs`), with a tokio `current_thread` runtime and a bucket client of its own,
  so that a renewal never waits for a turn of the loop. The loop reads the lease's expiry from
  an atomic and sends the thread commands; a lease that cannot be kept ends the process from
  that thread. Once the node serves, the thread also watches the loop: a count the loop
  advances while it makes progress (`kj_rs_tokio::watch_progress`, which misses the busy
  stretches that `progress.rs` names) that stands still for three leases (`Timing::stall_ms`,
  `cluster_logic::watchdog`) fences the node the same way.
- `kj::setupAsyncIo()` (which `//src/workerd/util:setup-async-io` supplies over kj-rs-tokio and
  kj-rs-io) is the same loop for the threads that block on a `kj::WaitScope` from C++: the
  inspector and fallback-service threads, and every `kj_test` binary.
- `setup-async-io` is linked per BINARY: `:workerd` (through `factory:bootstrap`) and every
  `kj_test` / `wd_cc_benchmark` binary link it (the macros add it); libraries do not depend on
  it, so a downstream binary linking workerd libraries keeps its own event loop. One exception
  for now: `//src/workerd/tests:test-fixture` still carries the dep so downstream binaries that
  link it without linking it themselves keep linking (TODO(cleanup) there; drop it once they
  depend on `setup-async-io` or `@capnp-cpp//src/kj:kj-async` themselves).
- Never depend on the `@capnp-cpp//src/kj:kj-async` umbrella: it drags in `kj-async-os`, whose
  definitions collide with the shim's (an ODR violation). Use `:kj-async-core` / `:kj-async-io`.
  `just check-io-backend-graph` (one `bazel cquery somepath`, run by the lint CI lane) rejects any
  such path from `:workerd`.
- Ownership: the returned `kj::AsyncIoContext` borrows a heap holder attached to its
  `lowLevelProvider`; the holder owns the tokio context and the inert event port, so the context's
  references are valid for its whole lifetime and torn down once. The inert `kj::UnixEventPort` is
  never driven (`KJ_UNIMPLEMENTED` if anything tries). I/O objects are used on the loop thread that
  created them (kj-rs-io checks and throws otherwise); the server's `Rc` state, kj-hyper's objects
  and the `loopback:` registry are likewise bound to the loop thread.
